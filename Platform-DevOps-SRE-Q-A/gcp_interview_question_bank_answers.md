# Senior GCP Cloud Architect, Platform, DevOps, and SRE Interview Answers

## Organization and access

### 1. A company has 200 GCP projects with inconsistent IAM and logging. How would you design the organization, folder, and project hierarchy and migrate toward a landing-zone baseline?

I would inventory projects, owners, IAM grants, logging sinks, network attachments, and data sensitivity before moving anything. The organization and folder tree should express policy boundaries, such as regulated versus general workloads and production versus nonproduction, while projects remain the primary workload, billing, and operational boundary. I would establish central audit-log exports, security monitoring, approved identity paths, organization policies, and project-vending templates first. Existing projects would be baselined in place in waves; I would test inherited policy changes in a representative folder before attaching them broadly. Success is measured by coverage of logging and ownership, time to provision a compliant project, exception expiry, and the absence of customer disruption during migration.

### 2. How would you decide project boundaries for production, teams, shared services, and regulated workloads while preserving billing and operational ownership?

I would use separate projects when teams need independent IAM, quotas, billing attribution, lifecycle, or incident blast radius. Production should not share a project with development; regulated data may require its own folder and dedicated projects, key ownership, and tighter access. Shared VPC host, security, and observability projects can be centrally operated, but team runtimes and data should usually be team-owned service projects. Labels and billing export make costs attributable; named service owners, deployment rights, and on-call escalation make incidents attributable. A project split is worthwhile only if its isolation benefit outweighs the operational cost of cross-project dependencies.

### 3. How would you combine organization policies, IAM, workload identity, and service-account impersonation to provide least-privilege access without long-lived credentials?

For people, I would use federated workforce identity and groups with narrowly scoped roles; privileged access should be time-bound and approved. For GKE, I would use Workload Identity Federation for GKE; for Cloud Run and VMs, attached service accounts; for external CI, Workload Identity Federation or a tightly controlled impersonation flow. Each workload gets a dedicated identity with permissions on the specific resource, while organization policies constrain risky configurations such as service-account key creation. I would audit token issuance, impersonation, and resource access, then rehearse revocation and failure of the identity provider. IAM grants permit actions; organization policies and resource-specific controls can still block them.

### 4. A developer requests broad Editor access to resolve a production issue. How would you provide a safer time-limited path and audit its use?

I would ask for the failing operation, target resource, and required duration before granting access. The safer path is a temporary role or custom role scoped to the affected project or resource, with approval, an incident ID, an expiry mechanism, and an operator assigned to verify removal. If the operation truly needs broad access, that should use a monitored break-glass path rather than permanent Editor membership. Cloud Audit Logs and deployment records should establish exactly what the developer changed. After recovery, I would reduce the permission to the minimum repeatable incident procedure and test it.

### 5. A workload cannot access a cross-project resource despite an apparent role binding. How would you investigate the effective principal, scope, inherited policies, and resource-level restrictions?

First establish the actual caller from the workload identity and denied audit event, not the identity the team expected to use. Check the permission and resource name in the error, IAM bindings and conditions at resource/project/folder/org scope, service-account impersonation rights if used, and whether an IAM deny policy or principal access boundary restricts the call. Then check relevant organization policies and resource controls such as Cloud Storage uniform bucket-level access, KMS key permissions, or a VPC Service Controls perimeter. I would reproduce with the same principal and request context, apply the narrowest correction, and confirm the audit event and application request succeed without widening unrelated access.

## Networking

### 6. When would you choose Shared VPC over isolated project networks? How would you allocate responsibility for subnet creation, firewall rules, and service-team access?

Shared VPC suits teams that need central IP planning, connectivity, firewall governance, and common egress while retaining separate service projects. The host-project team should own networks, subnets, routes, and guardrails; service teams receive only the subnet-use and workload permissions they need. Isolated VPCs are preferable when trust boundaries, independent routing, or regulatory requirements make shared networking too coupled. I would document DNS, firewall-rule ownership, egress, quotas, and incident escalation before onboarding teams. The deciding test is whether a change or outage in shared networking can disrupt unrelated products and whether the platform can operate that blast radius.

### 7. A service is reachable from one GKE cluster but not another. How would you trace DNS, routes, firewall policy, service endpoints, and return traffic?

I would compare a working and failing request from pod to destination: name resolution, resolved IP, source IP, destination port, timeout versus refusal, and trace or application error. Then compare Services and EndpointSlices, namespace NetworkPolicies, node and pod routing, firewall rules, and any private connectivity or service-mesh policies. For cross-project or hybrid paths, verify both forward and return routing, NAT, and DNS views; a healthy Service endpoint alone does not prove pod-to-backend reachability. VPC Flow Logs, firewall logs, and Connectivity Tests can narrow the network path, but I would also test the backend listener and application authorization before changing shared rules.

### 8. How would you compare Cloud VPN and Cloud Interconnect for a hybrid workload with defined availability, throughput, and cost requirements?

Cloud VPN is a good starting point when bandwidth needs are moderate, setup time matters, and encrypted tunnels over the internet meet the business requirement. Dedicated or Partner Interconnect is justified for sustained throughput, predictable connectivity, or a private hybrid topology, but requires circuit, location, partner, and capacity planning; encryption is not inherent to Interconnect. I would design redundant connections across failure domains, BGP routing, and a tested failover path rather than promising availability from one link. Compare measured peak and failure-mode throughput, latency, encryption requirements, lead time, and total cost, including egress and operational ownership. A failover exercise should prove customer transactions survive the expected link loss.

### 9. Design ingress for a global user-facing application with regional backends. How would you assess load balancing, Cloud CDN, Cloud Armor, health checks, and failover?

For public HTTP(S), I would evaluate a global external Application Load Balancer with regional backends, health checks that reflect readiness, and controlled traffic shifting. Cloud CDN should be limited to cacheable content with explicit invalidation and authentication rules; Cloud Armor policies should be tested for false positives during real traffic. Backend capacity and data consistency matter as much as edge routing: sending customers to another region is unsafe if it cannot serve writes correctly. I would test regional failure, bad releases, certificate rotation, origin health, and per-region synthetic transactions. The success measure is customer-visible availability and recovery time, not merely a green load-balancer dashboard.

### 10. A security team requires inspection of outbound traffic from multiple projects. How would you design egress without introducing a hidden shared failure point?

I would first identify which outbound flows actually require inspection; service-specific private access, restricted APIs, or direct egress may be safer than forcing everything through one appliance. For inspected flows, use a supported, redundant topology across zones or regions with explicit routing, capacity headroom, health checks, and controlled fail-open or fail-closed behavior based on data sensitivity. Cloud NAT provides translation, not deep-packet inspection, so it cannot substitute for a defined security control. I would test appliance loss, route rollback, DNS failure, and burst traffic while tracking customer latency and egress costs. Ownership of shared policy and emergency bypass must be explicit and auditable.

## Compute and GKE

### 11. How would you choose between Compute Engine, GKE, and Cloud Run for an API, a batch job, and a stateful service with different operational requirements?

For a stateless API, Cloud Run is often the lowest-operations choice if its request model, scaling behavior, and network integrations fit; GKE earns its cost when the team needs Kubernetes-specific scheduling or shared controllers. Batch jobs can use Cloud Run jobs for compatible workloads or GKE/VMs when runtime, networking, scheduling, or specialized hardware demands it. Stateful systems should generally use managed data services; use Compute Engine or carefully operated GKE only when the application requires host or storage control. I would compare startup latency, scaling limits, downstream capacity, operational staffing, availability, and cost under real traffic. A small production canary should validate the choice before a platform-wide standard is declared.

### 12. A regional managed instance group fails to scale during a traffic spike. How would you distinguish instance-template errors, quota, zonal capacity, health checks, and autoscaling configuration?

I would compare desired, created, and healthy instance counts and inspect autoscaler and managed instance group events first. If instances are not created, check quotas, zonal capacity, instance template validity, permissions, and recent placement or size constraints. If they start but never become healthy, inspect startup scripts, image changes, application logs, firewall reachability, and health-check path or timing. Preserve existing healthy capacity while reverting a suspect template or adding viable capacity in another zone; do not simply raise the autoscaling target. Verify recovery through healthy instances, queue or request latency, and customer error rates.

### 13. GKE pods remain Pending during a rollout while nodes appear healthy. How would you investigate scheduling constraints, node provisioning, pod IP capacity, and quota?

`kubectl describe pod` events tell me whether the pod is unschedulable or has been scheduled but cannot start; those require different checks. For scheduling, I would inspect requests versus node allocatable, taints, affinity, topology constraints, and namespace quotas. For capacity, I would inspect autoscaler events, node pool limits, project quotas, zonal capacity, and secondary range/pod-IP availability for the cluster's networking mode; a CNI IP allocation failure may appear after scheduling rather than as an unschedulable pod. PodDisruptionBudgets can block eviction of old pods during a rollout, but do not directly block scheduling new pods. I would keep serving capacity intact and verify both pod progress and customer health before relaxing constraints or increasing capacity.

### 14. How would you design GKE workload isolation and workload identity for teams with different security requirements? When would you choose separate clusters?

Namespaces provide useful ownership and policy boundaries but do not by themselves provide strong isolation from noisy neighbors, privileged workloads, or cluster-wide controllers. I would use per-team namespaces, RBAC, NetworkPolicies, resource quotas, admission controls, and dedicated Kubernetes service accounts with Workload Identity Federation for GKE. Bind a workload directly to the needed Google Cloud resources where supported, or use a scoped IAM service account path when needed; never share broad node identities for application access. Separate clusters when compliance, untrusted workloads, upgrade cadence, or blast-radius requirements cannot be safely satisfied within one cluster. Validate isolation with permission and network denial tests, not just configuration review.

### 15. How would you plan a GKE upgrade across production clusters, including workload compatibility, node disruption, add-ons, staged validation, and recovery?

I would inventory control-plane and node version compatibility, deprecated APIs, CNI and CSI behavior, admission webhooks, ingress, monitoring agents, and application disruption budgets. Upgrade a representative staging cluster, then a low-risk production canary before broader waves; verify rollback options separately for nodes and workloads, because control-plane downgrades may not be available. Keep spare capacity for node replacement, measure eviction and scheduling behavior, and set stop conditions on service SLIs. Back up workload data and configuration independently of the cluster upgrade. Completion means critical customer paths remain healthy through the rollout and a regional recovery test remains viable.

### 16. A Cloud Run service is fast in staging but times out under production bursts. How would you investigate concurrency, startup behavior, instance limits, downstream saturation, and retries?

I would correlate p95/p99 latency, instance count, startup latency, concurrency, request timeouts, max instances, and throttling with the release and burst window. Next I would check database connections, downstream quotas, and retries: raising instance limits can amplify an already saturated dependency. Mitigation might be traffic rollback, capped concurrency, controlled instance scaling, or queuing noninteractive work, depending on which path failed. I would test at representative load and observe error rate, tail latency, and downstream saturation together. Staging speed is weak evidence when staging has neither production concurrency nor production data access patterns.

## Data, delivery, and security

### 17. How would you choose among Cloud SQL, Spanner, Bigtable, and a queue or event service for a workload with explicit consistency, scale, and recovery constraints?

Start with invariants: transaction scope, consistency, access patterns, write rate, region and residency, RPO/RTO, and staffing. Cloud SQL fits familiar relational transactions and moderate scale; Spanner is justified when relational semantics and horizontal scale or multi-region requirements are demonstrated, not merely forecast. Bigtable suits high-throughput key/range access but is not a drop-in transactional SQL replacement. Pub/Sub decouples work and provides durable delivery, not a transactional system of record; consumers still need idempotency and replay rules. I would test peak and failure-mode workloads with cost and migration estimates before selecting a platform.

### 18. A Pub/Sub subscription backlog grows after a consumer deployment. How would you assess delivery, acknowledgment behavior, processing capacity, poison messages, and downstream health?

Compare publish rate, oldest unacknowledged message age, delivery attempts, ack latency, subscriber throughput, and dead-letter volume across the deploy boundary. If consumption slowed, distinguish application exceptions, downstream throttling, insufficient worker capacity, and repeated delivery due to missed ack deadlines. Check whether ordering keys or per-message work serialize throughput; adding subscribers may not fix a hot key. Protect correctness by making side effects idempotent and using bounded retries and dead-letter handling rather than dropping or blindly replaying messages. Customer impact is determined by end-to-end processing delay and failed business outcomes, not backlog size alone.

### 19. A Cloud Storage application receives permission errors after a policy change. How would you isolate identity, resource policies, organization controls, and network restrictions?

Identify the failing operation, exact bucket/object, and actual principal from the request and audit logs. Check IAM bindings and conditions, uniform bucket-level access versus legacy ACL assumptions, public-access prevention, IAM deny rules, and organization policies. If access crosses a VPC Service Controls perimeter, inspect perimeter violations and request context; encryption-key access can also block data operations. Reproduce with the workload's identity rather than an administrator account, then apply the narrowest policy correction. Confirm both legitimate access and intended denials, since broad read access to fix one error is not an acceptable production outcome.

### 20. How would you design build, artifact promotion, and deployment across projects using short-lived identities and verifiable supply-chain controls?

Build once in a trusted project, run tests and scans, record provenance, and promote the approved image by immutable digest rather than rebuilding from a tag. Use Workload Identity Federation for external CI or narrowly scoped service-account impersonation so deployments do not depend on stored keys. Target projects grant only the deployment identity and resource permissions required for that environment; approvals and policy gates bind to a digest and target. After rollout, query each target revision or running workload for the resolved artifact and compare it with the approved digest. If a copy to another registry reserialized the manifest, verify platform, image config and layer content against the approved build and attest the source-to-destination digest mapping; a signature over the source manifest does not validate the new manifest by itself. Record source commit, builder, both digests when applicable, approver, service account, target revision and customer-health result. Rollback uses a previously validated target artifact, not a rebuild assumed to be equivalent.

### 21. A Terraform deployment partially applies across several GCP projects. How would you establish the current state, prevent concurrent changes, and safely reconcile the deployment?

Pause concurrent pipelines and establish an incident owner before touching state. Compare the last approved plan, Terraform state and lock status, apply logs, and actual resources in each affected project; classify what was created, modified, or left uncertain. Do not force-unlock or reapply until the original runner is confirmed stopped, and do not manually delete a live resource just because the state view looks stale. Reconcile with import, state repair, or a reviewed corrective plan as appropriate, one bounded state at a time. Verify service health and a clean follow-up plan before reopening changes.

### 22. How would you evaluate organization policies, VPC Service Controls, encryption keys, and audit logs for a sensitive data platform? What limitations and recovery dependencies would you test?

Organization policies set preventive constraints, IAM limits who may act, VPC Service Controls reduce certain supported API data-exfiltration paths, and customer-managed keys provide control over key use and revocation. None replaces the others: VPC Service Controls is not a general firewall, and keys alone do not prove the workload can recover after a key outage. I would test perimeter access from approved and denied contexts, key disable/rotation and recovery, logging of data access where required, and backup restoration in another failure domain. Audit logs and retention must satisfy incident and regulatory needs without leaking sensitive payloads. Control design must document operational owners and a rehearsed break-glass path.

### 23. An alert reports unexpected service-account activity. How would you determine the affected principal and resources, contain access, and preserve evidence?

Build a timeline from Cloud Audit Logs: principal, token or impersonation path, source context, API calls, affected resources, and deployment changes. Determine whether access came from an attached workload identity, impersonation, or an exposed key; the containment choice differs. Remove the compromised grant or key and isolate the workload as needed, but assume already-issued access tokens may remain usable until expiry and block sensitive access at the resource boundary if immediate containment is required. Preserve logs and snapshots before cleanup, and check what actions succeeded, not just what the identity could theoretically do. Restore production on a fresh scoped identity and verify that both suspicious activity and customer impact have stopped.

## Reliability, cost, and migration

### 24. How would you define a customer-visible SLI and SLO for a multi-region GCP service and design alerts that distinguish user impact from telemetry failure?

Define the SLI from customer-visible successful requests or completed business transactions, with explicit latency thresholds, excluded traffic, and a measurement window. Report per-region and per-customer-segment results as well as the aggregate so a small geography cannot disappear inside global volume. Alert on short and long error-budget burn rates, using independent synthetic probes to detect telemetry gaps or a failing edge path. Monitor ingestion freshness and absence of expected samples separately; missing data must not be interpreted as success. Release policy should change when budget consumption exceeds agreed thresholds.

### 25. A service has an RTO of one hour and RPO of five minutes. How would you design and test regional recovery for compute, data, identity, and networking dependencies?

I would identify the durable write path and test whether the selected database replication and backup design can actually satisfy five minutes of data loss under load. Compute, Artifact Registry availability, secrets, KMS keys, DNS or load balancing, and identity must be ready in the recovery region; standby capacity has to be tested, not assumed. Rehearse regional failover with a recorded last durable transaction, switch write ownership exactly once, and verify an end-to-end customer transaction. RTO starts at the agreed failure or detection point and ends when the service is usable, not when the database starts. If either target is missed, report the gap and prioritize the limiting dependency before promising the objective.

### 26. A restore succeeds technically, but the application cannot use the restored data. How would you investigate data integrity, configuration, encryption, and dependent services?

I would check restore consistency and schema/application version first: a restorable database is not necessarily a compatible one. Then verify network reachability, database users and credentials, KMS decrypt permissions, connection settings, dependent object storage or event offsets, and whether all components were restored to a consistent point in time. Run business-level read and write checks against known records without corrupting the source or duplicating side effects. Keep the failed environment isolated until write ownership is clear. The next recovery test must measure usable application recovery, not just successful restore-job status.

### 27. GCP costs rise sharply in a shared billing account. How would you attribute the change to projects and usage, contain avoidable spend, and check the reliability impact of optimization?

Use Cloud Billing export to BigQuery to break down the delta by project, service, SKU, region, labels, and time; compare it with deployments and product demand. Look for retry storms, unexpected egress, logging growth, autoscaling, idle resources, or a new data-processing workload before cutting capacity. Apply a bounded containment action such as stopping a runaway job or rolling back a bad change, with the affected service owner present. Check customer SLIs, queue age, and capacity headroom after each optimization so cost savings do not create an outage. Long term, enforce ownership metadata, budgets and anomaly alerts, and a regular review of shared-cost allocation.

### 28. A database must migrate to GCP with minimal downtime. How would you design replication, data validation, cutover, rollback, and write ownership?

Inventory data model, extensions, connection behavior, batch jobs, and all writers before choosing a replication mechanism. Run initial copy plus ongoing change replication, validate row counts and business invariants, and measure lag at peak load. Rehearse a cutover with an explicit write freeze or controlled single-writer switch, validation gates, DNS or connection-pool handling, and a rollback cutoff. Once new writes land in GCP, rollback requires a proven reverse-replication or reconciliation strategy; pointing clients back to the old primary is not automatically safe. Define maximum downtime, acceptable data loss, and sign-off from the product owner before production cutover.

### 29. Tell me about a platform standard you introduced across teams with different levels of GCP expertise. How did you handle exceptions and measure adoption?

Use a real project rather than memorizing someone else's story. A strong answer has this shape: "Teams were blocked by [measured friction]. I owned [specific GCP standard and your contribution], tested it with [representative teams], and gave exceptions an owner, expiry, and migration path. After rollout, [before/after metric] changed, while [remaining cost or failure] led us to adjust [design decision]." For a project-vending or workload-identity standard, useful evidence includes time to first deployment, percentage of workloads using keys, audit-log coverage, exception age, and support tickets. Be ready to explain what *you* did, which teams resisted, and how the evidence supports the claimed outcome; do not present the example as your own unless it is true.

### 30. A global service's latency spikes in one geography while aggregate health appears normal. How would you distinguish client, DNS, load-balancing, CDN, backend, and dependency issues?

Start with geography-specific customer latency and request success, not aggregate load-balancer health. Compare client network and ISP patterns, DNS answers, CDN cache-hit and origin latency, load-balancer backend selection, regional backend saturation, and dependency calls for the affected cohort. Trace sample requests end to end and correlate with releases and routing changes; do not assume DNS is at fault just because the issue is regional. A safe mitigation might disable a bad backend, shift traffic, or roll back a region-specific release, provided destination capacity and data semantics allow it. Verify the affected geography recovers without degrading other users.

## Evidence-based exercises

### 31. A GKE workload uses a Kubernetes service account intended to access a resource in another project, but receives `403 Permission denied`. What identity, IAM, resource, and audit evidence would you inspect to identify the actual principal and denial?

Identify the Kubernetes service account actually used by the pod, its namespace, and its Workload Identity Federation configuration. Determine whether the request uses the workload principal directly or impersonates an IAM service account, then inspect the relevant binding on the target resource and any required impersonation grant. Compare the denied permission and principal in the API error and relevant Cloud Audit Logs with IAM conditions, deny policies, VPC Service Controls, and resource-specific controls; Data Access logs may need to be enabled and might not exist for the failed request. Retry from the same pod identity after a narrowly scoped correction; a successful test from a developer's account proves nothing about the workload. Record the change and confirm unintended principals remain denied.

### 32. A Cloud Run service's request latency rises from 300 ms to four seconds during a burst, while its database connection count reaches its configured limit. What additional evidence would you gather before changing concurrency or instance limits, and how would you limit impact?

The connection limit is a plausible bottleneck, not proof of cause. Compare Cloud Run concurrency, instance counts, request traces, connection-pool sizing per instance, DB active versus idle connections, lock waits, and error or retry patterns around the burst. More instances can worsen connection exhaustion; I would first protect the database with bounded concurrency, pool limits, load shedding or queuing, and possibly a rollback of the release. Test a representative burst while observing customer p99 latency and successful transactions. Increase capacity only after identifying the bottleneck and estimating the resulting total connection demand.

### 33. A regional managed instance group needs 20 healthy instances but has 12; new instances fail to become healthy after an image change. How would you separate provisioning, startup, networking, and health-check issues and decide whether to roll back?

Separate instance creation failures from unhealthy new instances using managed instance group and autoscaler events. Compare old and new template images, startup-script exits, serial-console or application logs, firewall policy, health-check port/path, and failures by zone. If the new image is the only changed variable and old instances still serve successfully, stop replacement and roll back the template before exhausting healthy capacity. If quotas or zonal capacity block creation, use approved alternate capacity rather than masking the issue with a health-check change. Confirm the group reaches its healthy target and customer errors and latency return to baseline.

### 34. A data service promises an RPO of five minutes, but the latest verified recovery point in a DR exercise is 15 minutes old. How would you confirm the measurement, determine customer impact, and improve the next test?

The five-minute RPO has not been demonstrated, but a 15-minute-old *verified* recovery point alone does not prove that newer writes were lost. Compare the failure timestamp, source commit log or application transaction IDs, replication position, restored data, and verification timestamps to identify the newest recoverable committed write. If committed writes from more than five minutes before failure are missing, the RPO target was missed; if the verification was stale, rerun it before drawing a conclusion. Determine which customer transactions are absent or need reconciliation before enabling writes, then test replication and failover under representative load. Report RTO independently: service restart time is not proof of usable recovery.

## Product-company practical exercises

### 35. A checkout service on Cloud Run begins returning `HTTP 503` during a promotion; its logs show request latency increasing before failures, but the database dashboard shows no obvious CPU spike. What evidence would you request next, and what mitigation would you choose while preserving data integrity?

I would pause promotion, quantify checkout failure by revision and region, and inspect Cloud Run request logs, instance counts, concurrency, startup and request timeouts, and any revision-specific configuration. Normal database CPU does not rule out connection saturation, locks, or retry amplification; inspect connection count, wait time, and failed transactions before scaling. If the previous revision remains healthy and data/schema changes are compatible, shift traffic back promptly while preserving logs and transaction integrity. If rollback is unsafe, cap new concurrency and isolate the failing request path while keeping writes single-owner. Recovery requires successful synthetic checkout and stable payment and error SLIs, not only disappearance of HTTP 503s.

### 36. A new product team needs a GCP project and production deployment within a day, while security requires audit logging and approved identities. How would you design the onboarding workflow and measure whether it is both safe and usable?

Provide a self-service project-vending workflow with mandatory owner, environment, cost center, and sensitivity metadata. Automation creates the project in the correct folder, links billing, configures approved identities, network access, centralized audit-log export, budgets, deployment roles, and basic observability before marking it ready. Fail closed when baseline controls cannot be attached, while allowing documented time-limited exceptions through a separate approved path. Give the team a tested sample deployment, not just an empty project. Measure request-to-first-successful-deploy time, control coverage, support tickets, exception expiry, and early production incidents.

### 37. A team proposes moving from Cloud SQL to Spanner after a traffic forecast doubles. What workload, consistency, migration, cost, and operational evidence would you require before approving the change?

I would ask for observed peak transactions, growth by tenant or key, query patterns, consistency needs, regional recovery goals, and evidence that Cloud SQL tuning or scaling cannot meet the forecast. Compare a representative workload on Spanner for transaction semantics, query design, latency, operational cost, and migration complexity; doubling traffic alone is not a sufficient reason. Prototype data and schema conversion, dual-write or replication risks, cutover, and rollback with explicit single-writer rules. Include cost at normal and peak utilization and the team's ability to operate the new platform. Approve only when the measured requirement and recovery benefit exceed the migration and ongoing complexity.

### 38. A Cloud Run revision begins returning `403` responses immediately after a secret rotation, while the previous revision remains healthy. How would you distinguish identity, secret-version, propagation, and application causes, limit impact, and verify recovery?

First identify where the `403` originates: the edge or Cloud Run invocation policy, application authorization, or a denied call to Secret Manager or KMS. Compare revision traffic, service-account identity, secret version selection or mounted secret configuration, IAM bindings, audit denials, and startup versus request-time failures. A secret-access denial usually manifests through application behavior rather than automatically becoming an HTTP 403 to the client, so I would not infer the layer from status alone. If the earlier revision and credential remain valid, shift traffic back while confirming that doing so does not violate the rotation or incident-response requirement; otherwise restore access narrowly to the new revision. Validate both secret retrieval and a real customer request, then retire the old credential only after the new path is proven.
